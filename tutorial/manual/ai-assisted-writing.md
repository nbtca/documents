# 用 AI 帮忙写文档

本文有两位读者：文档撰写者，和被要求写文档的 agent。撰写者读它，知道哪些事能交给 AI；agent 读它，知道该按什么规则写。核心规则只有一句：可以用 AI 起草，但每一条事实都必须由你核实后才能提交。发布后读者会照着做，出错的后果由协会承担，不由 AI 承担。

## 什么时候该用

给 agent 看这一段。它告诉 agent，什么时候该按这一页的规则写：

```yaml
name: nbtca-docs-write
description: Draft, organize, polish or translate a page of the NBTCA documentation site. Use when the member asks to write a page, turn notes or meeting records into a page, rewrite a draft, or translate a source into Chinese.
```

意思是：agent 被要求写一页、把会议记录整理成页、改一篇草稿，或把英文资料翻成中文时，先读这一页。如果把它做成可安装的 skill，这段就是 `SKILL.md` 的开头。

## 不可通融的规则

两条规则在每一步都成立：

1. **事实归作者**。版本号、端口号、命令参数、日期、人名和链接，都由你查证后写进去。agent 不确定的地方写 `待核实`，不猜，不编链接。
2. **归档只整理，不补全**。归档记录真实发生过的事。agent 可以把已有记录整理成条目、改通顺，不能产生原来没有的事实。缺失处标 `〔待核实：……〕`。

## 流程

agent 被要求写一页文档时，按这个顺序做：

1. **先读语域参考**。读一两篇本站同类页面，照着那个语域写。至少读 [终端、shell 与 PATH](/tutorial/terminal-shell-and-path) 和 [写一页文档](/tutorial/manual/writing-documents)。
2. **确认板块和读者**。问清楚这一页放在哪个板块、读者带着什么问题来。不同板块的写法不同，见 [写一页文档](/tutorial/manual/writing-documents#新建一页)。
3. **起草**。只写有依据的内容，每个结论附出处。具体写法见下一节。
4. **列清单**。写完单独列一份“我没有把握、需要你核实”的清单，这些内容不进正文。

## 哪些能交给它，哪些不能

| 任务 | 交不交 | 说明 |
| --- | --- | --- |
| 把会议记录整理成条目 | 交 | 只整理已有的内容 |
| 把句子改通顺、去掉重复 | 交 | 你已经写好意思 |
| 把英文资料翻成中文 | 交 | 作为理解的辅助 |
| 挑出语域和格式上的不一致 | 交 | 它指出，你决定改不改 |
| 提醒你漏掉的情况 | 交 | 答案要你自己验证 |
| 确定事实 | 不交 | 版本号、端口号、命令参数、日期、人名，都你自己查 |
| 生成参考链接 | 不交 | 它编的网址像真的，每个外链都要点开确认 |
| 写归档内容 | 不交 | 补全是伪造史料 |
| 整篇照抄它的输出 | 不交 | 照抄的中文容易识别 |

## 让它写出本站的样子

只对 agent 说“写一篇技术文档”，结果不符合本站的写法。给它下面这些约束：

1. 先读一两篇本站同类页面，照这个语域写。
2. 引号用 `“”`，不用 `「」`。
3. 不用破折号连接句子，不写“因此”“总之”“不难看出”这类过渡词，也不写“非常”“极大”这类没有数字的形容。
4. 每个结论附出处链接，链到具体条款，不链首页。
5. 命令给出 macOS、Linux、Windows 三种写法。

## 一段可以直接用的提示词

把下面整段发给 agent：

```text
我要给 NBTCA 文档站写一页文档，主题是（……）。

先读这两页作为语域参考：
https://docs.nbtca.space/tutorial/terminal-shell-and-path
https://docs.nbtca.space/tutorial/manual/writing-documents

要求：
1. 中文正文，代码和命令用英文。引号用中文双引号，不要用直角引号。
2. 不要用破折号堆句子，不要写“因此”“总之”“不难看出”这类过渡词。
3. 每个结论附出处链接，链到具体的条款或章节，不要只链首页。
4. 命令给出 macOS、Linux、Windows 三种写法。
5. 你不确定的地方直接写“待核实”，不要猜，不要编链接。

写完列一张清单，说明哪些内容你没有把握、需要我去核实。
```

最后一句让模型列出没把握的内容，这些内容就不会混进正文。

## 你负责核实什么

agent 交回草稿后，每一条事实都由你核实：

- **命令**：在你的电脑上运行一次。不能运行（例如你没有 Windows）时，在官方文档确认参数，或在文中注明这条命令没有经过测试。
- **事实和数字**：找到一手出处。规范查 RFC 或标准组织的文件，工具查官方手册，本仓库的情况查仓库中的文件。出处和锚点的写法见现有教程中的“延伸阅读”。
- **链接**：打开每一个链接。要批量检查站内链接，构建后运行：

  ```bash
  pnpm run ci:verify
  ```

  这条命令报告站内的失效链接和失效锚点。站外链接要你自己打开检查。

- **渲染结果**：AI 写的 Markdown 在本站可能不能正确显示。用构建产物判断，见 [VitePress](/tutorial/vitepress#验证要看构建产物)。

## 归档的红线

::: warning 注意
不要把 AI 生成的内容放进 `archived/`。`archived/` 是协会的史料。让模型补全一段“看起来合理”的会议内容，就是伪造记录。
:::

AI 可以把已有的记录整理成条目，或者改通顺。AI 不能产生原来没有的事实。原件缺失处，用 `〔待核实：……〕` 标注，写法见 [VitePress](/tutorial/vitepress#本站的编者按标记)。
